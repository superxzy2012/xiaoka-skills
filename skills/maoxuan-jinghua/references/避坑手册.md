# 大书蒸馏避坑手册

> 来源：《毛选蒸馏操作手册》（别人踩过的坑）+ 小卡 2026-10-02 亲踩的坑。
> 用途：任何 Agent 在做「书籍/大规模语料 → 技能」蒸馏前，先读这份清单。

---

## 一、拿源：先找 git，再试网络

**核心原则：公开经典文本几乎都有 GitHub 开源仓库。git 协议通常通，HTTP 抓取常常被墙。**

### 1.1 搜索姿势（命中率高 3 倍）

不要只搜书名。要**指定格式 + 平台**：

```
✅ "毛泽东选集 markdown github 开源电子文本"
✅ "<书名> epub txt github 开源"
❌ "<书名> 全文 在线阅读"
```

指定 markdown + github 的命中率远高于只搜书名。

### 1.2 选源标准（按优先级）

| 优先级 | 形态 | 说明 |
|---|---|---|
| 1 | 逐篇 markdown/txt | 结构清晰、可 grep 验证、无 OCR 成本 |
| 2 | 合并版 md/txt | 可用但篇目边界要自己切 |
| 3 | 带文字层 PDF | 可用，抽取稍慢 |
| 4 | 扫描 PDF | ❌ 成本高，最后考虑 |

### 1.3 clone 要点

```bash
git clone --depth 1 <repo>          # 大仓库必须 --depth 1
# 放后台跑，大仓库可能龟速
```

**小卡实测**：手册里写「该机 CDN 被墙」，但 `git clone` 直接成功，7 卷 392 篇 190 万字一次拉完。**别被"CDN 被墙"的记录误导 git 协议。**

### 1.4 拿不到源时，先问，再自己找

顺序：
1. 用户手上有没有文件？（**必须先问**）
2. 本地 NAS / Obsidian 库里有没有？
3. git clone 有没有？
4. 才有 web_search / web_extract / 浏览器自动化

## 二、代理与网络工具的真相

### 2.1 web_extract 后端可能是「残废的」

某些部署的 `web_extract` 走 Exa **keyless** 模式，行为是：**只从自己的搜索索引缓存取内容**。

| 现象 | 含义 |
|---|---|
| `CRAWL_NOT_FOUND` | URL 不在 Exa 索引里，它**根本没去请求那个站** |
| `Keyless Exa extract failed` | 同上，不是网络问题 |
| 返回 `Bad Content` | 索引里的页面本身就是残缺的 |

**推论**：改 URL 参数（`?offset=` / `?page=`）、换镜像节点、同一个文件换 4 个 CDN —— **全都没用**，因为请求根本没发出去。

**识别方法**：看错误文本里有没有 `Keyless`、`CRAWL_NOT_FOUND`、`Exa`。有 → 别再调参数了，换工具。

### 2.2 浏览器/CDP 自动化的真实边界

**能做的**：
- 连接已启动 `--remote-debugging-port` 的 Chrome
- `Runtime.evaluate` 读 DOM、跑 JS
- `Target.getTargets` 枚举标签页

**常做不到的**（除非 Chrome 启动时加了 `--remote-allow-origins=*` 且无其他限制）：
- `Page.navigate` —— 容易被拒（ConnectionReset）
- 在页面里 `fetch()` 外部 URL —— 同上

**判断方法**：握手成功 + `Runtime.evaluate` 成功 + `Page.navigate` 被 reset → **不是参数问题，是 Chrome 策略**。换 3 种 Origin 头还不行就停手，别陷进去。

### 2.3 playwright 的坑

`connect_over_cdp()` 在部分环境下握手失败，而裸 WebSocket 手写 CDP 却能通。两者不是一回事，别因为 playwright 失败就断定 CDP 不可用。

## 三、并行派发的坑

### 3.1 HTTP 503 会打断整个批次

大规模并行（5+ 个子代理读 100 万字）时，上游容量随时可能返回 `HTTP 503: capacity busy`。

**对策**：
- 每个子代理的任务要**幂等可重跑**，失败能直接重派
- 父代理保留完整 context 文本，重派时直接复用，不要重新生成
- **关键路径不要只依赖子代理** —— 容量掉了父代理要能自己顶上

### 3.2 context 必须自包含

子代理互相看不见。context 里必须写全：
- 书源绝对路径 + **只给它自己负责的那部分**
- 输出目录（独立目录，避免写冲突）
- 文件划分方案
- 强制模板（把章节文件该有哪些节写死）
- 验证要求（金句 grep 回源）

### 3.3 全局骨架必须父代理掌控

主 SKILL.md 由父代理亲写。子代理只见局部，让它们写全局会互相冲突且看不到跨卷脉络。

## 四、防幻觉：数据先验后报

**这是小卡今天犯的最严重的错。**

### 4.1 计数 ≠ 内容

我曾数「矛盾论 出现 2 次」就报告「15 篇里拿到 11 篇」。实际那 2 次**都在同一份目录页里**（`矛盾论 Bad Content`），真正文一篇没抓到。

**正确做法**：验证**内容**，不是计数。

```bash
# ❌ 只数篇名出现次数
grep -c "矛盾论" *.md

# ✅ 验证那句原文在不在
grep -l "主要的矛盾" *.md
grep -l "检验真理的唯一标准" *.md
```

### 4.2 关键命题必须逐条 grep 验证

蒸馏前先列一份「这份文本必须有」的命题清单（10 条左右），全部命中才说明源是真的：

```bash
for kw in "没有调查，没有发言权" "主要的矛盾" "具体地分析具体的情况" \
          "真理的标准只能是社会的实践" "集中优势兵力"; do
  n=$(grep -rl "$kw" --include="*.md" . | wc -l)
  [ "$n" -gt 0 ] && echo "✅ $kw" || echo "❌ $kw"
done
```

小卡实测：8 条命题里 2 条不命中 → 查出原文实际用词是「真理的标准只能是社会的实践」而非「检验真理的唯一标准」。**验证失败不是坏事，是发现了用词差异。**

### 4.3 不信子代理自报

子代理说「已回查 24 条金句」，父代理仍要随机抽 2-3 条独立 `grep` 复核。

## 五、方法论提炼的坑

### 5.1 保留原始概念名

不要用现代词替换：「矛盾」不能写成「冲突」，「群众路线」不能写成「用户思维」。替换后原文佐证对不上，且丢失历史语境。

### 5.2 决策规则要落到抽象层，但要注明原始语境

「当X时，做Y，因为Z」里的 Z 要说清原文的理由，同时标出它是在什么历史条件下说的（1930 年苏区 vs 今天）。

### 5.3 写清技能的边界

每章至少写一条「这个方法什么时候不适用」。《矛盾论》谈矛盾在事物中的地位，不等于给人排优先级；机械套用会退化成「永远只做一件事」。

## 六、三击换路规则（给小卡自己）

**同一目标连续失败 3 次，强制停下来换「类别」的路。**

不是换参数、不是换节点、不是换 Origin —— 是换根本不同的方案类别：

```
HTTP 抓取 → git 协议 → 问用户 → 本地库 → 浏览器自动化
```

小卡今天在 `curl / browser_exec / playwright / 裸 WebSocket` 上连打 9 次，全是同一类（HTTP/浏览器），且每轮失败原因略有不同，制造了"快通了"的错觉。**第 3 次就该停。**

配套纪律：**动手前先问「有没有现成的」**——用户手上、本地库里、已有技能里。用户发来的 PDF 里可能已经有答案了（《毛选蒸馏操作手册》里就写着确切的仓库地址和 clone 命令）。

## 七、抽取引擎自建要点

若上游 `extract.py` 缺失，按此实现：

- **CLI 契约**：`extract.py <路径>... --mode text|technical --install-missing ask|yes|no`，产物 `<workdir>/full_text.txt` + `<workdir>/metadata.json`
- **抽取链**：命令行工具（pdftotext/pandoc）→ Python 库（pymupdf/pypdf/markitdown/docx2txt）→ 内置纯文本解码
- **中文编码**：utf-8 → utf-8-sig → **gb18030** → big5 → latin-1 逐级回退，否则中文书全是乱码
- **阈值不能一刀切**：HTML/RTF 去标签后天然大幅缩水，用与 PDF 相同的最小字符阈值会把「短但抽取成功」的文件误判为失败
- **必须说清没有 OCR**：扫描件会失败，不要静默返回空
- **解释器问题**：系统 python3 常无 pip（PEP 668），依赖要装进独立 venv，并明确告诉用户用哪个解释器
