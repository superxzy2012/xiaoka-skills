# 交付验收（delivery acceptance）——观察模式、阈值与升级判据

轮询 worker 把 agent 的回答写进回执之前，可以加一道「这活能不能直接交出去」的判定。
本文件是这道闸门的决策表：怎么判、判多严、什么时候才允许真拦。

判定器本身（分类器调用形状、降级）见 `model-routing`；这里是**验收**这一层。

## 1. 闸门形态：先观察，后硬拦

| | 硬拦 | 观察模式（起步用这个） |
|---|---|---|
| 不合格怎么办 | 打回、标记失败 | 照常交付，只把结论写进回执 |
| 误判后果 | 好活被打回 → 任务死掉 | 无 |
| 能攒数据 | 只看得到被打回的 | 全部 p 值留档 |
| 什么时候能用 | 见 §4 三条前置 | 现在 |

回执字段（`outbox/receipt_*.json`）：

```json
"acceptance": {"p": 0.82, "pass": true, "why": "p=0.82", "mode": "jev"}
```

- `status` 永远只由调用成败决定，`acceptance` 是**上报字段**，不影响交付。
- `mode` 取值：`jev`（语义判定）/ `length`（被长度闸挡下）/ `degraded`（判定器不可达，放行）。
- 判定器不可达时必须 `degraded` 放行——决策层不能成为主流程的单点故障。
- 结果 MD 里同步加一段「## 验收（观察模式，未拦截）」，写明判定、p、依据、模式。

## 2. 样本矩阵（校准阈值前必须跑满）

只用「好活 / 烂活」两个样本校准阈值，必然把某一类判错。这七类都要有：

| 类别 | 样本形态 | 期望 |
|---|---|---|
| 短·正确 | 「毛利率 32%，回款周期 45 天。」 | PASS |
| 短·敷衍 | 「已完成。」/「好的，我马上处理。」 | FAIL |
| 长·凑字数敷衍 | 一百多字「非常重视…认真研究…全面考虑…」无任何事实 | FAIL |
| 长·好 | 带数字、带价格带、带回本周期的分析 | PASS |
| 列表·好 | 三条要点，每条有实质内容 | PASS |
| 代码·好 | 可直接运行的脚本 | PASS |
| 代码·空壳 | `def process(): pass` | FAIL |

**凑字数那一类是最值钱的**——人最容易漏判、也最费时间；语义判定对它很准（实测 170 字空话 p≈0.05），别用长度去代理质量。

**每个样本必须配自己的 `requirement`。** 用同一条要求（如「一句话回答价格指数在哪个菜单」）去判十个不同类型的交付物，选品分析/脚本都会因「答非所问」拿到 p≈0.02——看着像判定器坏了，其实是判对了。自造样本时 `(requirement, deliverable, 期望)` 三件套一起写，缺一样这轮回归就是废的。

## 3. 两个会系统性判错的坑

- **长度闸不能当质量代理。** 用 30 字符做下限，会把「毛利率 32%，回款周期 45 天。」这种完美短答案 100% 误杀（p 直接记 0，语义判定根本没跑）。下限只用于挡「已完成。」这类纯敷衍，取 **8 字符**：8 字以上全部交给语义判定。3 字符以下（如只回「32%」）确实无法脱离问题判对错，属于可接受的漏判。
- **思维链污染会被判成低分，而且判得对。** 模型把英文思考过程写进正文时，交付物本身就是半成品，p 落在 0.4–0.5 是**正确**判定，不是误判。遇到这种情况先修输出（提问时加「只给最终答案、不要输出思考过程」后缀，或过滤 `reasoning` 帧），不要去调阈值把分数糊上去。
- **判定口径只能写进 `state`，不能加长 `instructions`。** 在 `instructions` 里追加「简短不是缺陷、一句话答对就算 PASS」这类补充，实测**所有样本 p 一起崩到 0.0x**（连原本 0.82 的好答案也掉到 0.03）。要调口径就在 `state` 末尾加中文【判定口径】，`instructions` 保持两句话不动。
- **短答案的 p 天生偏低，靠阈值校准而不是靠改 prompt。** 一句 36 字的正确结论 p≈0.53，同样内容写成 137 字带数据则是 0.81。试过三种强化口径的 prompt，p 反而更低（0.45→0.38）——这是判定器对篇幅的固有偏好，改不动。短答案多的场景把阈值往下调，别硬掰 prompt。

## 4. 升硬拦的三条前置

全部满足才允许真拦，缺一条就是给自己挖坑：

1. **攒够 100 个真实样本**（不是自造样本）。
2. **人工抽查误判率 < 2%**：随机抽 20 个回执，逐个核对 `acceptance.pass` 与人工判断是否一致。
3. **打回能自动重投 `inbox/`**，并带重试计数上限。文件总线没有重试机制，打回即任务消失——这条链路没建好之前，硬拦 = 交付凭空蒸发。

## 5. 按交付物类型分层（最终形态）

| 交付类型 | 判法 |
|---|---|
| 报告 / 分析 / 文案 | 语义判定（本文档的闸门） |
| 短答案 / 数值查询 | 只做 8 字符下限，不判语义 |
| 代码 / 脚本 | **跑一遍**（语法检查、执行、单元测试），不靠语义判定——它只能判「像不像能跑」，判不了真能不能跑 |
| 发给 BOSS 本人的交付 | 优先级最高，返工成本高，值得拦一道 |

## 6. 阈值怎么扫、p 稳不稳

- **每个样本只算一次 p，阈值在本地扫。** 判定器每次调用 0.4–1.4s，按每个候选阈值把样本矩阵重跑一遍纯属浪费。拿到每个样本的 p 之后，用同一批 p 在 0.30 / 0.35 / 0.40 / 0.45 / 0.50 / 0.55 上各切一次，输出「阈值 → 准确率 → 错判样本名」表，安全区间一眼可见。
- **先验证 p 是稳定量，再谈阈值。** 同一交付物连跑 5 次，`sd` 应在 0.02 以内；抖到 0.2 以上说明单次 p 不可用于判定，得先固定 seed 或换判定器。实测一批真实回答 sd = 0.00–0.02，判定稳定不是噪声。
- **安全区间常常很宽，取中段。** 实测 0.30–0.50 全部 100% 准确（10 个样本），0.55 才开始误杀短答案。贴着边界取值（0.30 或 0.55）一换样本就翻车，取区间中段稳。
