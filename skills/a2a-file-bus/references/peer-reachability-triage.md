# peer / 中继端口可达性分层判定

适用：要判断「某个 peer 或中继机的端口，从某台机器能不能通」，以及不通时卡在哪一层。
典型场景：给外部 peer 开隧道前先确认它能不能到中继机；或者两边各说各的「我这边是通的」。

**核心原则：单边的 CLOSED 不是结论。** 必须先排除「测的人自己出不去网」，再谈目标侧。

## 第一步：带对照组的探针

`nc` 不一定装（容器里常常 `command not found`），用 bash 内建的 `/dev/tcp` 等效——它同样会发真实 SYN：

```bash
export TZ=Asia/Shanghai
date '+%H:%M:%S.%N'
timeout 5 bash -c 'exec 3<>/dev/tcp/<TARGET>/<PORT>' && echo OPEN || echo "CLOSED rc=$?"
date '+%H:%M:%S.%N'
```

**每次都带一个已知可达的对照组**（国内直连稳的公网 IP:443，如 `223.5.5.5`）：

- 对照组 OPEN + 目标 CLOSED ⇒ 本机出网正常，结论指向目标侧。
- 对照组也 CLOSED ⇒ 先修自己（代理/路由/出网），此时目标的结果无意义。

从**容器和宿主机各测一次**：容器 NAT 与宿主路由可能不同，一边不通不代表另一边不通。

## 第二步：用「耗时」区分丢包和被拒

没有 `nc` 就没有 `refused`/`timed out` 的文字可读，但**行为本身就是判据**：

| 现象 | 含义 |
|---|---|
| `rc=124`（`timeout` 到点杀掉），耗时**精确满** 5.0s | SYN 发出去**零回应**（丢包/被静默 DROP） |
| 立刻返回非 0（毫秒级） | 收到 **RST** = `Connection refused`，有主机但没有服务在听 |

所以**一定要把起止时间打出来**。只看「CLOSED」两个字，丢包和被拒无法区分，而这两者的处理方向完全相反：
前者要查防火墙/安全组，后者要查进程有没有起来。

## 第三步：目标侧自查（把「本机零拦截」坐实）

在目标机上一次性拿齐四项，否则结论不硬：

```bash
ss -tlnp | grep -E ':(22|443)\b'        # 必须 0.0.0.0 / ::，不能是 127.0.0.1
ufw status                              # inactive
sudo iptables -L INPUT -n --line-numbers # policy ACCEPT，且没有针对公网源的 DROP
ip -4 addr show | grep inet             # 关键：公网 IP 在不在网卡上
```

**云主机（EIP）的公网 IP 通常不在网卡上**（网卡只有私网 `10.x`）⇒ 入站必须先进云平台的安全组/NAT
才能转到本机。所以「本机监听正常 + ufw 关 + iptables 放行 + 外部探测超时」基本就等价于
**安全组未放行**，而不是本机防火墙问题。

## 第四步：双边抓包对账（把「包到底到没到」变成铁证）

目标侧只抓**入站 SYN 无 ACK**，避开自己往外的流量：

```bash
tcpdump 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0 and (dst port 22 or dst port 443)'
```

两边都要秒级时间戳（探测侧 `date '+%H:%M:%S.%N'`，目标侧 tcpdump 自带）。判据三选一：

| 探测侧 | 目标侧 | 结论 |
|---|---|---|
| OPEN | 有 SYN | 链路通，可用 |
| CLOSED / timeout | **无 SYN** | 包根本没到目标 ⇒ **上游拦截**（安全组/运营商），与目标主机零关系 |
| CLOSED / timeout | 有 SYN | 包到了没回 ⇒ 回程/应用层问题，另一个方向 |

第二行是最有价值的结论：**无 SYN = 铁证**，不用再靠猜，也不用再让人去控制台翻规则。
注意：对照组（如 `223.5.5.5`）是**出站**，不要让它进目标侧的入站抓包日志，否则干扰判读。

## 两条独立出口不要串成一条链

「NAS 出口」和「peer 沙箱出口」是**两个独立数据点**，必须分别测、分别记：

- peer 侧也 CLOSED ⇒ 确定是目标侧未放行，开防火墙这一步绕不过；
- peer 侧 OPEN ⇒ 只是某一侧出口受限，中继对它本来就通，可能根本不需要改安全组。

**不要因为「等安全组」就把 peer 侧的探测也停了**——把两个视角串行化会白白多等一轮，而且丢掉那个能决定
方案选择的数据。同理，只读探测与「账号是否禁用」「是否发凭据」完全无耦合，可以并行。

## 交付回执的写法

只写四样：① 出口公网 IP（让对端知道日志里该找哪个源）② 每个目标的起止时间到纳秒 ③ 是超时还是被拒，
以及依据（耗时满 5s vs 毫秒返回）④ 对照组结果。不要写「应该是安全组的问题」这类推测——把数据给对方，
让对方用自己的日志下结论；两边结论不一致时，先对时间窗口，再怀疑对方。
