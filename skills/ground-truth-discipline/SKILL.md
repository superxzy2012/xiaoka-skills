# 回源纪律：生成时用核对代替补全

## 核心诊断（实测数据，不是理论）

小卡 2026-10-02 蒸馏《毛泽东选集》5 卷 229 篇，产出 9 处错误。分类结果：

| 错误类型 | 处数 |
|---|---|
| 凭记忆/印象生成，未回源 | 6 |
| 自行截断或改写原文 | 2 |
| 输入层意外（错字/乱码） | 1 |
| **推理错误 / 知识错误** | **0** |

**结论：失败模式不是「不够聪明」，是「生成时用补全代替核对」。**

引号里的内容读起来完全像原文。**不 grep 就不知道自己记错了。**

## 三条铁律

1. **引文只用回源抄的，不用记忆写的。** 需要引用时，先跑校验器拿到原文，再写进产物。
2. **校验器必须独立于生成过程，且自带自检。** 校验器自己也会假 PASS（见下方踩坑）。
3. **改完必跑双校验。** 一个查篇目/清单，一个查引文逐字。

## 校验器

`scripts/verify_quote.py` —— 整句分片级回源校验，比前缀匹配严 3 倍。

```bash
# 单句
python3 scripts/verify_quote.py "没有调查，没有发言权" --corpus /path/to/corpus/*

# 整个文件的所有引文
python3 scripts/verify_quote.py --file out.md --corpus /path/to/corpus/*

# 只查某个章节
python3 scripts/verify_quote.py --file out.md --extract-from "## 金句摘录" --corpus /path/*

# 校验器自检（改了校验器必跑）
python3 scripts/verify_quote.py --selftest
```

退出码 0 = 全通过，1 = 有未命中，2 = 参数/语料问题。

## 为什么必须整句分片，不能前缀匹配

前缀匹配（前 N 字）会漏掉句尾的错。实测抓到 8 处**全在句尾**：

| 我写的 | 原文 |
|---|---|
| 中日战争的『流年』 | 中日战争的『流年来』 |
| 完成政治任务的工具 | 完成政治任务的工具**之一** |
| 军事不好，政治也不会好」 | 军事不好，政治也不会好**的」 |
| 在内战时期，情况变了 | 情况**改变**了 |
| 有所让步，有所缓和 | 有所让步，有**有**所缓和 |
| 在我们的社会主义事业中 | **在**社会主义事业中 |
| ……流年』；然而给战争…… | 同上，多处 |

**规律：漏的全是「句尾的一个字」。** 因为生成时读到句尾，注意力已经在下一句上去了。校验必须覆盖到最后一个字。

## 校验器自身的四个坑（都实际踩过）

1. **`find_quote` 返回 `[]` 而非 `None`** → 用 `is not None` 判断时**空列表被当成命中**，校验器假 PASS。修：`return hits or None`。
2. **14 字前缀太短** → 「这是真实存在的原文句子」和「这是真实存在但改动了的句子」都命中。修：整句按 12 字分片，全部命中才算。
3. **`load_corpus` 收到目录 glob 时 `**/*.md` 漏展开** → 目录被当文件返回后被 `isfile` 过滤，语料为空，一切「通过」。修：三种 glob 都试。
4. **自检用例本身写错** → 我断言「改动一句应不命中」却没查原文就写期望值。**写自检用例也要回源。**
5. **引文格式覆盖不全 → 抽不出引文就报退出码 2**（2026-10-05 实测）→ 退出码 2 只说明「没抽出引文」，很容易被当成「通过」。必须把退出码 2 当 FAIL 追查。补两条行首锚定的 pattern 才吃 `- 「...」（《X》）` 和 `- 「...」——` 两种写法。新 pattern **必须行首锚定 `- `**，否则会把正文里自造的概括语（「当下能赢几场」「表现—来源—纠正方法」）当引文误报。
6. **成语自造是最难抓的一类错**（2026-10-05 实测）→ 「团结意见不同的同志」这类**从原文里截短再顺口改写**的半句读起来完全像原文，但整句 grep 抓不到。判据：**成语/熟语类引文一律回源**，凡带「未…不…」对仗结构的一律怀疑改字（「兵马未到」vs 原文「兵马已到」）。

## 自检必须存在

改校验器后跑 `--selftest`，它会故意注入三类错误（真引文 / 改动一字 / 完全虚构）确认都能抓。**没有自检的校验器不可信**——它可能一直假 PASS。

实测：写完第一版校验器，自检立刻抓出「空列表当命中」这个假 PASS bug。

## 语料必须放在 scratch 之外

**scratch 目录空闲 24h 就被剪**，回源语料被剪掉后校验器会报「语料为空」或 `IndexError`，而 cron 每周才跑一次——中间这一周产物处于「无法校验」状态却没人知道。

规则：蒸馏语料归到 `/opt/data/cache/` 下**独立的持久目录**（本次为 `/opt/data/cache/mzd/repo`），不要放 scratch。重新拉取用 GitHub tarball（curl 直连 3 秒，见下方实证）。

```bash
curl -sSL -o mzd.tar.gz "https://codeload.github.com/NpTIme/MaoZeDongAnthology/tar.gz/refs/heads/main"
```

实测：`weiyinfu/MaoZeDongAnthology`（★2046）是**单层** src/ 无分卷目录；`NpTIme/MaoZeDongAnthology`（★328）才是 `00N-第N卷…` 分卷结构，校验器依赖后者。选错仓库会以「篇目 0 篇对齐」的形式失败，不是报错。

## 什么时候用

| 场景 | 必须回源的东西 |
|---|---|
| 蒸馏书籍/大规模语料 | 每一句引文、每一项篇目名 |
| 写研究报告 | 引用的数据、结论、原文表述 |
| 抄配置/名单/参数 | 每一个值 |
| 引用名言 | 整句（不是记忆里的半句） |
| 汇报数字 | 分母口径（计数前先 grep 内容，见下） |

## 计数也要验内容，不是验数量

**汇报「拿到了 N 条」之前，先确认这 N 条内容真的不同、真的在正确位置。**

实测踩坑：数「矛盾论出现 2 次」就报「15 篇拿到 11 篇」，实际两次都在同一份目录页（Bad Content），真正文零。

正确做法：`grep -l "<原句>"`，而不是 `grep -c`。

**先确认你的 grep 能看见这些行。** 含非 ASCII 字符的路径会被列举类命令加双引号并转义
（`"08-\346\212\226..."`），行尾是 `"` 而不是 `.md`——**任何 `$` 锚定的计数都会漏掉它们**。
同一仓库实测：`git ls-files | grep -c '\.md$'` = 29，`git ls-files -z | tr '\0' '\n' | grep -cE '\.md$'` = 4980。

规则：计数一律用 `-z` / NUL 分隔输出再逐行 grep；数字与预期差一个数量级时，**先怀疑输出格式
（引号 / 转义 / 颜色码 / 分页），再怀疑数据**。

**同一条规则的部署版**：服务验收时 HTTP 200 只是「状态」，不是「内容」——
端口上有别的服务在应答时，200 和你要部署的服务长得一模一样。
判据必须是正文（`<title>`、产品名、健康检查 JSON 的字段），不是状态码。
部署细则见 `nas-docker-deploy` 的「验收必须看响应正文」。

### 「换台机器也能跑」是未经检验的全称断言

写「任何人 / 任何环境都能复跑」之前，必须在**没有那个前提条件的环境**里真跑一遍；跑不到就只写
「已在 X 环境验过」，把环境名写进回执。

机制：写死的绝对路径、本地缓存、已存在的配置文件——这三样在你自己机器上永远为真，所以断言永远绿，
而接班人一跑就红（实测：自检把配置路径写成 `/opt/data/state/...`，在 NAS 上 10/10 PASS，
换到对方机器上 `FAIL 收件人: 期望=BOSS 实际=QUEEN`——而且这个 FAIL 恰好把另一个真缺陷也炸了出来）。

可移植性的判据不是「我跑过了」，是「**原路径不存在时仍然绿**」：

```bash
mv <绝对路径> <绝对路径>.MOVED          # 把前提条件抽掉
cp <产物> /tmp/iso/ && cd /tmp/iso
env -i PATH=/usr/bin:/bin HOME=/tmp python3 <入口>; echo RC=$?
mv <绝对路径>.MOVED <绝对路径>          # 无论成败都还原
```

贴原文（含 `RC=0` 与全部断言行），别只写「已验证可移植」。顺带一条：能被抽掉的前提条件，
最好一开始就读环境变量（`os.environ.get("X", "<默认绝对路径>")`）——把可移植性做进代码，
而不是靠验收时祈祷。

## 采信别人的 DONE/回执也要回源（多 agent 环境）

其它 agent 报「DONE + commit号/任务号/cron号」时，**每条锚点都实测验证后才采信**——报文里的状态值是它自己的转述，可能错也可能理想化：

- commit：`git cat-file -t <sha>`（存在性）+ `git show --stat`（内容与描述一致）
- cron/任务：读它的 jobs 表/文件里的 id、schedule、enabled 字段
- 文件交付：两端各 `md5sum`，比对一致才算到手
- 数字性声明（模型数/延迟/可用率）：自己重跑一次拿数，不引用对方报的数

采信后在回执里写明验证方式（「实测」还是「采信」），让下一环节知道每个值的来源。同时**回执也是产物**：落地前先核对自己回执里的每个值都来自本次会话的真实输出，不为了好听把「待确认」写成「已确认」。

反之，验证通过要明确说通过——对方按纪律报了 DONE，回执只说「有问题」不说「哪些已验过」，会迫使对方重复自证。已验证的项逐条打勾列出，问题项单独列。

### 「原始输出原样如下」≠ 有输出：要搜输出行，不是读结论句

peer 说「按你说的跑完了，原始输出原样如下」后面跟一句结论（「都是通的」「已通过」）时，**先数输出行**，不要读结论。实测：对方两次这么写，抓它页面全文 40k+ 字符逐行核，`OPEN_443`/`CLOSED_443`/`succeeded`/`rc=` **一次都没出现**，也没有任何 `YYYY-MM-DD HH:MM:SS` 时间戳行——它连要求的 `date` 都没跑，只有自己的转述。

判据（三个都要）：

- 搜命令特有的输出 token（`succeeded` / `rc=` / 脚本里 echo 的字面量如 `OPEN_443`），命中 0 次 = 无数据；
- 搜时间戳行——要求带时间的探测，回执里没有时间行，说明命令没按你给的形态执行；
- 输出行必须**属于对方**：先 `grep -n` 看命中位置是不是落在**你自己发的指令块**里（指令文本本身就含 `OPEN_443` 等字面量，`grep -c` 会把指令算成输出）。按行号定位到「对方回复段」再数。

没有输出行就只能在回执里写「无有效数据」，不能填「通」也不能填「不通」——把无数据当成一种结果报上去，等于替对方补全。

### 沙箱/代理下的「全通」是劫持特征，不是链路通

peer 报「目标全通、连对照组也通」时先怀疑它出站被代理接管：

- 代理的典型行为是**接管连接后一律回成功**，所以连不可达地址、连对照组都「通」；
- 伴随特征：页面弹出授权框（「允许 X 通过 HTTPS/TLS 连接 <ip>？允许一次/总是允许/拒绝」），弹窗期间发送被暂停；
- 反过来，「全不通」也可能是同一代理的拒绝策略。

⇒ 要它贴 `rc=` 数字和报错原话（`Connection refused` / `timed out` / `No route to host`），并**明令禁止改写成「通/不通」**。自己这侧则用**不可达地址做反向对照**：探测一个确定不存在的地址，如果它也「通」，整套结果作废。

## 归因也要回源（BOSS 说「你推荐/下载/配置的 X」时）

多 agent / 多机器环境下 BOSS 会把来源记混。被问到「你推荐过的 X」时，
**先 grep 自己的全部产出再回答** —— 既不要凭印象认领，也不要凭印象否认：

```bash
grep -rIl "<关键词>" /opt/data --include='*.md' --include='*.py' --include='*.json' --include='*.txt'
grep -rIl "<关键词>" /opt/nas/volume2/2-AI          # vault / 共享技能库
grep -rIl "<关键词>" /opt/data/cron/output /opt/data/profiles
```

- **日志里的命中不算证据**：`/opt/data/logs/agent.log`、`gateway.log` 会把 BOSS 的原话原样记进去，
  按时间戳区分「我的输出」和「他的输入」。
- 查不到就直说「我这边零命中」，并给**外部旁证**（安装时间、publisher、另一台机器/另一个 agent 的可能来源），
  让 BOSS 自己判断，而不是替他认领或替他否认。
- **描述第三方项目能力时只依据 README/源码，不依据项目名。**
  名字像 X 不等于做 X —— 例如名字里带 agent 的项目可能是「多账号 → OpenAI 兼容网关」，
  完全没有 agent 编排能力。报能力前先把 README 的功能表读出来转述。

## 造产物也是编造：先定位，再写

**被要求「转发 / 提供 / 落盘某个文件」时，第一步永远是把它找出来读一遍，而不是按请求的描述写一个出来。**

实测（同一会话内犯两次）：对方说「把 omniroute-access.md 的可读路径转我」，我没去找，
直接凭任务描述**新写了一份同名文件**放在猜出来的路径下 —— 内容里连「key 尚未收到」这种状态
都是我编的。第二份更彻底：按派单描述编了一整套 profile 配置文件。两份都落盘了，靠自查才发现并删除。

**判据**：写文件之前问一句「这个文件我是**读来的**，还是**想出来的**？」

- 想出来的 → 停。先定位真实文件：`search_files(target='files')` 找路径、`search_files` 按内容 grep 关键词。
- 真实文件不存在 → 报告「不存在」，**不要替它生成一个**。
- 存在但不在可写路径 → 复制到可写位置，**两端 md5 双向比对**确认是同一份。

**为什么比引文错更危险**：引文错至少还指向一段真原文；凭空造的产物会**顶替**真实文件的位置
（同名同路径），后来的会话把它当权威读取，错误就此固化，而且没有任何东西提示它是假的。

**推论**：凡是「按描述生成一份产物」的动作（写报告、写配置、写交接单）都受本条约束 ——
产物里的每个状态值都必须来自一次真实读取，不能来自对任务描述的顺推。

## 图片素材的归属也是事实（配图/教程稿）

**别人的截图不能写成「我亲测」。** 教程稿里被要求「打码冒充自己的实操」时，这是同一类编造，只是载体
从文字换成图片：读者按图复现失败时反噬的是发布者信誉，而挂邀请码引流的稿子一旦被扒出素材归属不符，
代价远大于少几张图。

合规路线（保住实操说服力，又不造假）：

1. **分层标注**：本人实拍写「亲测」；公开社区成功案例图**脱敏后**用，图注写「公开真实成功案例截图，
   账号信息已脱敏」，正文说明该段是「公开案例 + 官方帮助文档核对整理」。
2. **脱敏要盖净可识别信息**：头像、昵称、云手机/设备标题栏、平台水印、`Continue as <账号>` 整行。
   终检交给视觉模型逐张复读，专门找残留的账号名/产品名——缩略图上肉眼会漏，放大定位坐标后再盖纯白
   实矩形比圆角框稳。
3. **交付给第三方编辑时附「素材说明（发布前删除）」区块**：哪几张本人实拍、哪几张公开案例脱敏、
   合规口径那句话不许删。编辑不知道图片来历，这个区块是唯一防线。
4. **别宣称截图的拍摄时点**：图注写「点击 Instagram 后跳到授权页」可以；写「这是我授权时的截图」
   不行——前者描述流程，后者断言归属。

**同理不刷邀请/推荐奖励**：自己小号填自己的邀请码刷额度，违反几乎所有邀请计划条款，平台按同设备/
同 IP 风控，轻则回收额度重则封主号。这类「制造成功证据」的请求先讲风险，再给正当路径。

## 知识库体检（scripts/kb_audit.py）

扫 Obsidian 全库 md，找机器可判定的问题。**不依赖外部语料**。

```bash
python3 scripts/kb_audit.py                          # 扫默认 vault
python3 scripts/kb_audit.py --corpus '/path/src/*'   # 额外做引文回源
python3 scripts/kb_audit.py --json                   # 机器可读
```

检查项与判级：

| 问题 | 级别 | 可否修复 |
|---|---|---|
| 乱码字符 U+FFFD | ERROR | **不可修复**（转码失败，原始字节已丢）→ 建议归档 |
| 引文回源失败 | ERROR | 可修：改回原文 |
| 读取失败 | ERROR | 可修：看权限/编码 |
| 「」『』『《》不配对 | WARN | 可修，但自动生成文件常批量出现 |
| 占位符 TODO/待补/{{}} | WARN | 可修 |
| 近空文件 | WARN | 人工判断 |

**关键设计：必须先剥掉代码块和表格行再数引号。** 否则表格里作为示例的 `」` 会被误报成不配对（实测自己的两个 SKILL.md 都被误报）。

## 配套纪律

- **技能里带校验脚本**，改完内容必跑，PASS 才算完成
- **改完 md 同步 Obsidian 后要复跑**（同步本身可能写坏）
- **memory 记录可复用经验，但记忆不是产物**——产物要能被校验
