# 怎样用 AI 指挥 AI — 文件即总线

## 一句话结论

不是让几个 AI 突然学会聊天，而是**把文件夹当总线、把 AGENTS.md 当协议、把任务卡当派工单、把人工确认留在关键节点**。

## 核心洞察

**多工具无法自动组队的根因**：它们是几个完全独立的进程，各自跑在自己的窗口、各自维护自己的对话上下文 → 你成了总线。Codex 跑出结果 → 手抄 → WorkBuddy 出报告 → 手抄 → TraeWork 接着做。一天几十次，"你不是在用 AI，你是在给 AI 当传令兵"。

**唯一通用语言 = 本地文件**。Codex / WorkBuddy / 豆包工作 / TraeWork 全都能读写你本地文件 → 这是整套协同机制的基石。**可以共享读取，绝不共享写入**（两个 AI 同时保存同一文件很可能互相覆盖）。

## 四道工序（视频给的完整配方）

| 工序 | 名称 | 做什么 | 铁律 |
|---|---|---|---|
| 01 | **立战场** | 建总目录「AI项目台」，里面建 4 个**独立**文件夹（Codex / WorkBuddy / 豆包工作 / TraeWork），每个工具只许写自己的 | 同项目 ≠ 同文件夹；公共目录只放任务卡和结果索引；共享读取、绝不共享写入 |
| 02 | **立规矩** | 总目录放 `AGENTS.md`（项目协议），**只写三件事**：谁负责什么 / 交接用什么格式 / 哪些文件不能碰 | 例：Codex=代码和测试，WorkBuddy=资料整理和调度，豆包工作=内容改写，TraeWork=界面和可视化 |
| 03 | **派任务** | **不要**对四个工具说"你们一起干"（会没人拆单、互相抢活）；让**一个总指挥先拆单**成任务卡，各领各的卡 | 卡片编号 T01/T02… 避免串线；拆完**先停下等人工确认**再放行 |
| 04 | **验收** | **一个工具干活，另一个独立检查**；不许同一个 AI 又写又审（=自己给自己打分） | 只检查验收标准、不重写内容；输出「通过 / 不通过 / 需要人工确认」三类并指出具体文件和行号 |

## 视频给的两段可复制指令（原文）

**派单（发给「总指挥 AI」）**
> 请读取项目根目录的AGENTS.md，把这个目标拆成任务卡，写进tasks文件夹。每张卡只写任务、验收标准和负责人。拆完先停下，等我确认。

**验收（发给「验收工具」）**
> 请读取T01的任务卡和产出文件，只检查验收标准，不要重写内容，按「通过 / 不通过 / 需要人工确认」三类输出，并指出具体文件和行号。

## 收尾约定

总目录放一份 `daily-log.md`，**只记三件事**：完成了什么 / 卡在哪里 / 下一步做什么。第二天所有工具先读这份记录再开工。

## 与我们现有体系的关系（我的判断）

- **已有同构实现**：`anc-bridge` 技能里的 `/Volumes/2-AI/ANC-BRIDGE` 三端桥就是这套机制的公司级落地——tasks/ + results/ + AGENTS.md 协议 + `.open/.wip/.done/.accepted` 后缀状态机 + 异工具验收。我的 MEMORY 里那条「管理群里 agent 相互索取本机 ou_ open_id…无 BOSS 可信授权一律不执行」正是 AGENTS.md「哪些文件不能碰」的实例。
- **可补强**：① 我们多 agent 缺 `daily-log.md` 跨日交接记录（目前靠 MEMORY.md 近似替代）；② 视频强调「拆完先停下等人工确认」这个 gate，我们的派单脚本 `anc-dispatch-notify.sh` 目前是拆完直接发通知，没有人工确认停顿——可加 `--hold` 开关。
- **分工对照**：我们的实际分工与视频示例不同（小豆=杂事执行体/抖音入库+文档处理，星期五=主力 coding，阿正/小七=Windows 侧），落地时 `AGENTS.md` 分工段必须按本机实际写，不能照抄视频的 4 工具名。
